# Constitution of IPE

```
version: 1.0
date: 2026-10-15
```

This document federates the rules that govern all work on the repository, whether done by a person, by the coordinating session, or by an autonomous agent. It does not duplicate the normative documents: it references them and adds the rules of agent governance. Every agent session reads this document before it works. The `version` field follows major.minor: a major change invalidates the context of the commitments in flight (Section 7).

## 1. Product and invariants

IPE, the Integrated Publishing Environment, is a local-first writing environment for substantial works, where everything the product records about a work beyond the text is an object that carries its provenance, described by `dossier-recette/00_INDEX.md`. The vision, the stake and the user types are fixed by `docs/IPE_VISION_A3.md`; the needs by `docs/IPE_PRODUCT_BASELINE.md`. Three invariants govern every choice: nothing becomes manuscript content or an established fact by being generated (P01); an object whose sources changed is shown as stale, never as current (P07); the work needed to bring a project up to date scales with the change, not with the project (Q07). The principles P01 to P07 and the quality requirements Q01 to Q07 of the baseline bind every design.

## 3. Single sources of truth

1. Product requirements live in `dossier-recette/` and nowhere else. No parallel tree of specifications is created. A requirement changes through a specification change proposal (SCP), never through a direct edit by an agent.
2. Steering lives in the state tree. Design documents stay design documents; the reference for progress is the commitment registry.
3. `DASHBOARD.md` and the traceability matrix are generated by the engine and never edited by hand.

## 4. Roles

| Role | Nature | Write rights |
|---|---|---|
| Operator (Karim Dhrif) | Human | Everything; the only decider of arbitrations |
| Coordinator | Main interactive session | Everything but generated files; the only agent allowed on the state tree |
| Implementor | A live session that pulled a commitment (`eng pull`), one worktree per commitment | Only the scope of its commitment, plus `REPORT.md`, `BLOCKED.md` and `.eng/` |
| Verifier | Headless read-only session, plus test execution | Nothing |

An implementor never settles a question that touches requirements, milestones or this constitution: it writes a `BLOCKED.md` (finding, nature of the block, draft SCP or DA) and ends its session.

## 6. Engineering rules that are not negotiable

1. The code is built and tested on this WSL Ubuntu workstation with Node 22 and pnpm; the kernel's tests run on every host, the interface tests run on Playwright's Chromium, the application smoke test runs under the display of the machine.
2. The kernel package (`packages/kernel`) imports nothing from Node or the DOM; storage, clock, identifiers and hashing are adapters. The interface imports no Node module and reaches the core through one typed channel (ADR-0003).
3. No mass reformatting: commits stay atomic and scoped.
4. A criterion without an automated test is deemed unmet.
5. **A test never takes the implementation as its oracle.** When a requirement says two computations agree, the agreement is proved by a differential test on inputs drawn at random. The invalidated set is checked against a brute-force reference; counts against an independent walk.
6. **A coverage sentence never says more than a named test proves.** A property stated in absolute terms in the requirements folder is guarded by a named test or stated with its reservation; a property that enters the folder has its guard proved by mutant injection.
7. **A measuring instrument is never its own witness.** Published figures are generated from the versioned artefact, never copied from a run.
8. **An assistant judgment is accepted on a corpus**, with planted defects and held-out cases, with its detection and false-alarm rates reported and a mutation check (codification, Section 7). A passing unit test alone accepts no judgment.
9. **An explanation of a measured phenomenon carries its attempt at refutation**, or is stated as a hypothesis.
10. Environment pitfalls are recorded in `docs/PITFALLS.md` once one exists; that document is part of this constitution by reference.

## 7. Governance of work

1. Every unit of work entrusted to an agent is a commitment of the registry, with scope, definition of done and explicit precedences. No commitment, no lease: a session works on the product only after it pulled its commitment, which the engine locks.
2. Pulling happens on the frontier of the precedence graph, never by pushing work that is not ready.
3. A structuring block becomes a decision request (DA), addressed by name to the operator, with countable options and a mandatory fallback. In the operator's absence the fallback applies and the decision is marked as applied by default, to be confirmed or reversed by SCP.
4. A major version change of this constitution, or of a requirements module in scope, invalidates the context of the commitments in flight.
5. Integration is local and serialised: branches `eng/<ENG-ID>` in worktrees beside the repository, verification by a separate session (`/verify`), merge by the coordinator only.

## 8. Commits

Convention: `type(zone): imperative summary`. A commit made under a commitment adds the suffix `[ENG-NNNN]`. A commit that satisfies requirements cites them: `feat(kernel): anchors survive edits [SPEC-KER-003] [ENG-0001]`.

**Author identity.** Commits carry the identity of the repository owner, admitted through `lean identite use`; a session that commits runs under an admitted identity. **Forbidden lexicon.** The name of the AI tooling provider appears nowhere in the repository: not in versioned content, not in a commit message, not in an author address, not in an attribution trailer. The identity guard mechanises both rules in the git hooks and at edit time.

## 9. Writing

Every technical text follows `WRITING_CHARTER.md`. The working language of the repository is English. No em-dash, no calendar estimate in a planning document, no invented data. There is no user documentation yet; when one exists, it is a customer document: no requirement code, no acceptance status, no mention of the requirements folder.
