## Context

The product connects the Claude provider through its Messages API (DA-0004, decided). That API is reached on a host name, and every request carries a version header, and both identifiers contain the company name of the vendor of the agent tooling used on this repository. The writing charter of the repository (CONSTITUTION.md, Section 8, enforced by the guards `guard_style` and `guard_identite`) forbids that name anywhere in versioned content, in a commit message and in an author address, with no exception for a third party's technical identifiers. The delivery of ENG-0005, held on 2026-10-16, therefore assembles the host and the header name from fragments at run time (the constant `VENDOR` in `packages/providers-claude/src/index.ts`), exactly as the engine's own guards do, and the test TST-PRV-007a holds the source to it: the repository stays free of the name, and the product speaks the documented API. A reader of the adapter sees fragments where the provider's documentation shows the plain identifiers.

## What is at stake

The adapter is held and works; nothing of the product waits. What waits is the readability of the adapter and the rule itself: every future provider adapter, fixture and documentation line that must quote the provider's host or header name will follow the same detour, and a reviewer who compares the source with the provider's documentation must reassemble the fragments to check them. If the question is not taken, the detour stands by default and the rule stays simple.

## Closed question

Do the provider's API identifiers (its host name and its version header name) stay assembled at run time, or are they exempted from the forbidden lexicon and written in clear: A or B?

## Options and consequences

**A. Keep the rule as it is, the identifiers assembled at run time, as delivered.** Changes nothing in the repository. Costs one indirection in each adapter that speaks that provider's API, and a test per adapter that holds the source to it; a reviewer reassembles the fragments to compare with the documentation.

**B. Exempt the provider's API identifiers from the lexicon by an allowlist in the charter check, and write them in clear.** Changes the charter check of the engine (an allowlist of exact technical identifiers: the host name and the header name, nothing else), then one edit of the adapter and its test. Costs a change of the engine, which lives in another repository, and a rule with an exception that must be stated in the Constitution; the vendor's name then appears in the versioned source, in the two technical forms only.

| Criterion | A: assembled at run time | B: allowlist for the API identifiers |
|---|---|---|
| Change to the repository | none | the adapter, its test, CONSTITUTION.md Section 8 |
| Change to the engine | none | the charter check, in the engine's repository |
| The vendor's name in versioned content | nowhere | in two technical identifiers only |
| Source readable against the provider's documentation | after reassembly | directly |

## Recommendation

**A.** Nothing is lost: the adapter is held, TST-PRV-007a proves the identifiers it sends, and the rule keeps no exception. Option B buys readability of two lines at the price of a change in another repository and an exception written into the Constitution. What remains unknown: whether a later provider adapter will need more such identifiers, which would reopen the question with more weight.

## Concrete example

The adapter sends its requests to a host built as `https://api.` followed by the vendor's name and `.com`, and a header whose name is the vendor's name followed by `-version`, with the value `2023-06-01`. Under A, the source holds the fragments and TST-PRV-007a asserts the assembled host and header name against the recorded exchange. Under B, the source holds the two identifiers as the provider's documentation prints them.
