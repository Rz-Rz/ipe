## Context

DA-0002 fixed local-first operation with the desktop as the first surface and a browser surface later, on condition that one core serves both and that the interface is built in browser technology. The baseline (Section 2) leaves frameworks, editors and desktop wrappers open and asks that technical choices be made against the needs and recorded. The build machine was surveyed on 15 October 2026: Node 22, pnpm, a Rust toolchain, Playwright Chromium builds, Google Chrome, Xvfb and a WSLg display, the shared libraries a Chromium-based shell needs, an Electron download in the local cache; the WebKitGTK library a Tauri shell needs is absent and its installation requires administrator rights that no session holds. The company's existing interfaces are React 18 with Vite; the steering engine is TypeScript.

## What is at stake

The provenance kernel (milestone J-KER) is the first code written. Its language and its boundary with storage and interface decide whether the browser surface reuses it or rewrites it, and whether the first release can be tested as a user on this machine without administrator rights.

## Closed question

Which stack carries the first release: A, B, or C?

## Options and consequences

**A. TypeScript core, Node adapters, React and Vite interface, Electron shell.** The kernel is a package with no Node and no DOM dependency; storage is an adapter interface implemented on Node for the desktop; the interface runs in a browser window and reaches the core through a message channel. It costs the Electron footprint and a code-signing step per operating system later.

**B. Rust core, Tauri shell, React interface, WebAssembly build for the browser later.** The kernel is a Rust crate compiled native and to WebAssembly. It costs a second build target, a bridge between the interface and the crate, and the WebKitGTK prerequisite that this machine lacks.

**C. TypeScript core and a browser application first, desktop wrapper later.** The same core as A, served as a web page using the browser's file system access. It costs the files-on-disk promise where that access is unavailable, and reverses the order DA-0002 fixed.

| Criterion (countable, sourced in the survey of 15 October 2026) | A | B | C |
|---|---|---|---|
| Prerequisites present on the build machine without administrator rights | all | WebKitGTK absent | all |
| Build targets for one core on both surfaces | 1 (the same bundle runs in Node and in the browser) | 2 (native and WebAssembly) | 1 |
| End-to-end testing as a user on this machine | Playwright on Chromium, Electron under the WSLg display or Xvfb | blocked by the missing library | Playwright on Chromium |
| Alignment with code the company already maintains | React, Vite, TypeScript (interfaces and engine) | Rust (Agelaios core) | React, Vite, TypeScript |
| Files on disk in documented formats (P05) | yes, through the Node adapter | yes | not in every browser |
| Vim-style editing (N20) | CodeMirror 6 with its Vim extension | same interface | same |
| Extension languages reachable (N20) | JavaScript natively; Lua through WebAssembly | both through the bridge | same as A |
| Packaged application size, order of magnitude | hundreds of megabytes | tens of megabytes | none |
| Order fixed by DA-0002 | kept | kept | reversed |

## Recommendation

**A.** It is the only option whose every prerequisite is present here, it keeps one build for both surfaces, it matches the company's interface stack and the engine's language, and it can be tested as a user on this machine. Its cost is the application size, which no need of the first release constrains. What was checked: the survey above. What remains unknown: the packaged size on each operating system, and code-signing, both outside the first milestone. Conditions attached: the kernel package imports nothing from Node or the DOM; storage, clock and random sources are adapters; the interface never imports Node modules and reaches the core through one message channel, so the browser surface reuses it unchanged.
